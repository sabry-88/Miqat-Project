## 1. Project Identity & Design Philosophy

- **Brand & Audience:** **Miqat Hajj & Umrah Platform** — tailored for adults (ages 35–85) requiring high readability, calm visual hierarchy, and institutional financial trustworthiness.
- **Visual Tone:** Calm, mature, institutional ("Warm Ivory" in Light Mode; "Night in Makkah" deep navy-slate in Dark Mode). Aggressive font weights, giant decorative KPIs, clutter, blur/glassmorphism (unless explicitly approved), and generic AI-dashboard styling are **strictly forbidden**.
- **Operational Workspace Scope:** Accounts Workspace modules operate as a static multi-page application (MPA) with mock data (`accounts-mock-data.js`) and shared controller (`accounts-workspace.js`). Never invent backend/SQL/API calls, real downloads/restores, or fake cryptographic verification claims. Any simulated action must be explicitly labeled as simulated.

### Mandatory Typography Constraints
1. **Tabular Numerals:** Declare `font-variant-numeric: tabular-nums; font-feature-settings: "tnum" 1;` on all prices, amounts, dates, IDs, counts, sizes, and phone numbers.
2. **Zero Letter-Spacing in Arabic:** Never apply `letter-spacing` to Arabic script (breaks cursive joins/tashkeel). Restrict negative/positive tracking strictly to `[dir="ltr"]`.
3. **Diacritic Protection:** Keep Arabic line-height `>= 1.3` (`>= 1.42` with `padding-top` on headings carrying tashkeel; `1.55` where dense RTL pills/headers wrap).
4. **No Forced Uppercase:** Never apply `text-transform: uppercase` to English labels or table headers; use natural Sentence Case or Title Case.

## 4. Cards, Containers & Component Sizing

### Standard Content Cards (`.acc-card`, `.acc-filter-card`)
- **Surface:** `background-color: var(--color-surface); border: 1px solid var(--color-border);`
- **Radius:** `10px`–`12px` (`var(--radius-md)` / `var(--radius-lg)` depending on container level).
- **Padding:** `16px 20px` (or `20px 24px` for root/filter cards on desktop) / `14px 16px` on mobile.
- **Shadow:** Use `var(--shadow-sm)` in Light Mode (`styles.css` `.acc-card` currently uses `0 1px 3px rgba(0, 0, 0, 0.04)` as an existing source value); `none` or `var(--shadow-sm)` in Dark Mode.
- **Sibling Gap:** `14px`–`16px` (or `24px` between major page sections).

### KPI Summary Cards (`.acc-kpi-card`)
- **Grid:** `display: grid; grid-template-columns: repeat(auto-fit, minmax(210px, 1fr)); gap: 14px;` (use `minmax(0, 1fr)` inside narrow/mobile rules).
- **Equal Heights:** `display: flex; flex-direction: column; justify-content: space-between; min-height: 118px; padding: 14px 16px;`
- **Icon Box:** `34px × 34px`, `border-radius: 8px`, `16px × 16px` SVG glyph, background `var(--color-surface-secondary)`, icon color `var(--color-secondary-blue)` or `var(--color-accent)` (dark: `var(--color-link)` / `var(--color-accent)`).
- **Structure:** Top row (icon + label) → Middle row (`1.30rem` tabular value) → Bottom row (`0.74rem` descriptor).

### Container Rules & Practical Card Usage Decision Rule
- **Public Global Containers:** `.container` (`max-width: var(--container-max)` = `1320px`; `padding-inline: clamp(16px, 4vw, 28px)`), `.container-narrow` (`880px`), `.auth-card` (`480px`), `.auth-card-wide` (`540px`), `.auth-card-choice` (`700px`).
- **Accounts Main Content (`.acc-main-content`):** `flex: 1; min-width: 0; padding: 24px 32px 60px; display: flex; flex-direction: column; gap: 24px;` (collapses padding on tablet/mobile).
- **No Card Overload:** Avoid unnecessary nested cards-within-cards.

#### A. When a Card Is Required
Use an established card/container (`.acc-card`, `.acc-filter-card`, `.acc-kpi-card`) when content represents a coherent functional group, such as:
- KPI or financial summary.
- Related information belonging to one record or entity.
- A filter group.
- A form or set of related actions.
- A table or structured data section.
- A distinct operational section that needs visual separation.

#### B. When a Card Is NOT Required
Do **not** create a separate card for:
- Every individual text line.
- A simple page subtitle.
- A short explanatory sentence.
- A small label or metadata item already belonging to another component.
- Decorative content without a functional grouping purpose.

#### C. Mandatory Preservation Rule
When an approved page or existing component already uses a card/container to group important content, do **not** remove that structure simply to make the page look minimal, and do **not** leave important grouped content floating directly on the page background.

> **Main Principle:** Use cards to communicate meaningful grouping and hierarchy — not as decoration and not as wrappers for every line of text.

## 7. Arabic / English Localization

1. **Zero Leaked Translation Keys:** `t(keyPath, defaultText)` and `applyTranslations()` must **never** render raw keypaths (e.g., `accounts_workspace.*`, `modifications.*`) into the DOM. Always validate resolved strings and fall back safely to `defaultText`.
2. **100% Arabic Mode (`<html lang="ar" dir="rtl">`):** All UI labels, placeholders, buttons, table headers, badges, empty states, dialogs, tooltips, validation messages, dates, and dynamic JS content must be in Arabic. No stray English UI labels.
3. **100% English Mode (`<html lang="en" dir="ltr">`):** All UI strings and mock datasets rendered in the UI must be in English. Zero Arabic characters (except explicitly approved brand/proper nouns if specified) and **strictly Latin numerals (`0-9`)** — zero Eastern Arabic-Indic numerals (`٠-٩`).
4. **Number, Currency & Metric Formatting Rules:**
   - Use the established workspace formatting helpers — `AccountsWorkspace.formatNumber()` / `AccountsWorkspace.formatCurrency()` (`accounts-workspace.js` L75–88) — or the target module's existing localized formatter where applicable. **Do not** introduce independent number-formatting logic that conflicts with existing workspace behavior.
   - **Arabic Numeral Presentation (Verified Codebase Behavior):** Do not invent a new numeral policy. `accounts-workspace.js` (`L59–88`) uses `toArabicIndicDigits()` with Arabic separator `،` for `'ar'` and `toWesternDigits()` for `'en'`; most workspace modules (`accounts-bookings.js`, `accounts-cancellations.js`, `accounts-reports-backup.js` L903, `accounts-report-details.js` L325, `accounts-report-export.js` L465) use `toLocaleString('ar-EG')` for `'ar'` and `toLocaleString('en-US')` for `'en'` (note: `accounts-collections.js` L40 / `accounts-collection-details.js` L24 use `'en-US'`). Always inspect the target module's existing implementation before editing.
   - Dates, amounts, percentages, phone numbers, and technical IDs must remain readable and correctly ordered in **both** RTL and LTR (wrap mixed LTR/numeric tokens like `1.8 MB`, `2026-11-23`, `REP-...` in `<bdi dir="ltr">` / `dir="ltr"`).
5. **Live Switching Without Reload:** Language toggles must re-render static `[data-i18n*]` elements AND all JS-rendered values, labels, tables, KPIs, dropdowns, modals, and active states (e.g., active simulation step text) consistently via `AccountsWorkspace.onPageRefresh(...)` without resetting active in-page state or reloading.
6. **Cross-Page Persistence:** Persist language in `localStorage` (`miqat_lang`).

## 8. RTL / LTR Implementation

- **Logical CSS Properties Mandatory:** Always use `margin-inline`, `padding-inline`, `border-inline-start`, `border-inline-end`, `inset-inline-start`, `inset-inline-end`, and `text-align: start` / `end` instead of physical `left`/`right`.
- **Directional Drawers:**
  - Anchor new drawers logically with `inset-inline-start: 0` and `border-inline-end: 1px solid var(--color-border)` (avoid physical `right: 0`/`left: 0`; note legacy `.mobile-nav-content` at `styles.css` L1440–1450 still uses `right: 0`/`left: 0`).
  - Retain direction-aware physical X-axis `transform` slides (CSS `translateX` is physical): `[dir="rtl"]` slides from `translateX(100%)` → `translateX(0)`; `[dir="ltr"]` slides from `translateX(-100%)` → `translateX(0)`.
- **Directional Isolation for Technical Data:** Wrap or attribute technical IDs (`BK-20261123-0400`, `REP-20261123-01`), ISO dates (`2026-11-23`), times (`09:30`), file sizes (`1.8 MB`, `2.84 GB`), percentages (`73.4%`), `SHA-256` strings, and English parentheticals with `dir="ltr"` or `<bdi>` / `.rep-table-mono` so punctuation never inverts (e.g., `)Every 12h(`).
- **Icons & Arrows:** Check back/next arrows, chevrons, breadcrumb separators, and table alignments in **both** RTL and LTR.

## 10. Dark Mode Requirements

- **"Night in Makkah" Atmosphere (Token Reference):** Always use `var(--color-bg)` (`#172838`), `var(--color-surface)` (`#22384B`), `var(--color-surface-secondary)` (`#2B4358`), and `var(--color-input-bg)` (`#1A2D3D`) — reference values shown for clarity; write `var(--color-*)` tokens in CSS, never raw hex. **Never use `#000000` (pitch black)** and **never leave white `#FFFFFF` cards/backgrounds** in Dark Mode unless explicitly approved.
- **CRITICAL Contrast Rule (`--color-primary` vs. `--color-link`):**
  - `--color-primary` in Dark Mode is `#2B4E70`, which on `#22384B` cards yields ~1.4:1 contrast (WCAG failure).
  - Therefore, **never** use `style="color: var(--color-primary)"` inline on text/values/headings. Use semantic CSS classes (e.g., `.rep-text-brand`, `.rep-val-primary`) that resolve to `var(--color-primary)` in Light Mode and **`var(--color-link)` (`#8AB7E0`)** or `var(--color-text)` (`#F5F2EB`) in `[data-theme="dark"]`.
- **Gold Background Text Contrast (Token Alignment & Scoped CSS Exception):**
  - `--color-accent-text` in `[data-theme="dark"]` (`styles.css` L160) is `#E5C98A` (radiant gold text for dark navy surfaces), **not** dark text for gold backgrounds, and `:root` defines no `--color-on-accent` token.
  - On **solid Gold backgrounds** (`var(--color-accent)` / `var(--color-accent-hover)` / `var(--color-accent-rich)`), never put white `#FFFFFF` or `#E5C98A` text. Reuse the existing `.btn-accent` class (`color: #0B131D`, `styles.css` L661–687) or existing scoped `styles.css` gold-button/badge rules (`#183653` / `#12202D`, hover `#0A141E` at `L1885`, `L5957`, `L19968`, `L19976`, `L32173`). Do **not** introduce new arbitrary hex values outside those already established in `styles.css`.
- **Muted Text & Borders:** Use `--color-text-muted` (`#D0D9E2`) and `--color-border` (`#334D64`) instead of light-mode shadows.
- **Check All States:** Inputs (`color-scheme: dark`), radio/checkbox (`accent-color: var(--color-accent)`), modals, tooltips, empty states, hover, focus, and active tabs.

### Theme Contrast Verification Rules (Light & Dark)
- **Documented Tokens ≠ Automatic Proof:** Having approved tokens in CSS does not guarantee every pair has sufficient contrast.
- **Measure Actual Pairs:** Measure actual foreground/background contrast for normal text, important labels, buttons, status pills, placeholders, and interactive states (`:hover`, `:focus-visible`, `.is-active`, `:disabled`) in **both** Light Mode and Dark Mode.
- **No Unverified Claims:** Never claim a contrast requirement passed unless an actual measurement or reliable automated check was executed in the target theme. Explicitly record any unverified combinations as requiring validation.
- **No Unauthorized Color Changes:** Never alter approved Miqat colors without measured failure evidence and explicit user authorization.

## 12. Zero Horizontal Overflow Rules (Section 6 — Mandatory)

*(Preserved in full from `.agent/rules/RESPONSIVE_DESIGN_GUIDELINES.md` Section 6)*

> **Mandatory Core Directive:** Every Miqat page must remain fully contained within the available viewport width at all supported responsive breakpoints.

1. **No Unintended Horizontal Overflow:** No page, workspace, or main content section may create unintended horizontal overflow or activate a viewport horizontal scrollbar (`document.documentElement.scrollWidth <= document.documentElement.clientWidth`).
2. **Zero Clipping & Total Containment:** No text, card, button, badge, table control, or interactive element may be partially clipped, cut off at viewport edges, or extend outside its parent container.
3. **Adaptive Card Reflow:** KPI cards and other repeated card groups must use responsive layouts (flexible grids or auto-wrapping flex rows) that reflow into additional rows when width decreases, rather than forcing a single rigid horizontal row.
4. **Header & Action Group Wrapping:** Page headers, toolbars, and action button groups must adapt using flexible wrapping (`flex-wrap: wrap`) and responsive stacking instead of forcing a fixed horizontal row.
5. **Complex Activity Row Wrapping:** Activity rows, notification feeds, and complex list items must wrap or stack appropriately on smaller screens, keeping descriptions, timestamps, and action buttons visible and accessible.
6. **Flex & Grid Shrink Capability (`min-width: 0`):** Flex and grid children must be allowed to shrink. Explicitly declare `min-width: 0` on flex items and use `minmax(0, 1fr)` in CSS grids so intrinsic child size never expands parents past the viewport.
7. **Safe Text Wrapping & Controlled Widths:** Never use fixed pixel widths exceeding available content width or unconstrained `white-space: nowrap` that causes viewport overflow.
8. **Bidirectional RTL and LTR Verification:** Verify both RTL (Arabic) and LTR (English) layouts across breakpoints; never assume LTR safety guarantees RTL safety.
9. **Contained Horizontal Scroll for Tables:** Data tables may use a dedicated, intentionally contained horizontal scroll container (`.acc-table-responsive` with `overflow-x: auto; -webkit-overflow-scrolling: touch; min-width: 0; max-width: 100%;`) when columns genuinely require it—without ever overflowing the page or `.acc-main-content`.
10. **Multi-Breakpoint Viewport Validation:** Verify across desktop (`1440px`, `1280px`), tablet (`1024px`, `768px`), and mobile (`390px`/`375px`, `320px`), including intermediate widths where reflow occurs.
11. **Direct Rendered DOM Inspection:** Inspect actual rendered bounding rects and `scrollWidth` vs `clientWidth` in browser to confirm nothing is clipped, hidden behind sidebars, or inaccessible.
12. **Universal Future Page Application:** Applies permanently to all current and future Miqat pages, components, and workspaces.

> **IMPORTANT:** Never hide horizontal overflow by adding `overflow-x: hidden` on root containers to mask broken sizing. Fix sizing, flex shrinkage (`min-width: 0`), and wrapping at the source.

## 19. Commonly Repeated Mistakes — STRICT UI MISTAKE PREVENTION RULES

**These are mandatory engineering prohibitions and validation requirements — NOT optional suggestions.**

### A. Card Design & Dimensions
- Never create cards with arbitrary or inconsistent dimensions; related cards must follow a consistent sizing system.
- Use appropriate card heights based on content (or flex equal-height rows for sibling KPI cards), never arbitrary fixed heights that clip or leave empty voids.
- Align cards cleanly within their grid/layout; maintain consistent padding (`16px 20px` / `14px 16px`), gaps (`14px–16px`), border radius (`10px–12px`), and alignment.
- Do not make cards unnecessarily tall, wide, crowded, or oversized.
- Do not create a card for every small line of text, and do not remove a card/container when content clearly belongs inside the established card-based layout.
- Never place important standalone content directly on the page background when the established module design uses a card or structured container.
- Avoid unnecessary nested cards and containers; validate card sizing across desktop, tablet, and mobile.

### B. Typography & Font Sizes
- Do not use arbitrary font sizes; follow the established Miqat typography scale (`1.35rem` page title, `1.05rem` card title, `1.30rem` KPI value, `0.82rem` body/table/buttons).
- Maintain clear hierarchy across page titles, section headings, card titles, body text, labels, helper text, and metadata.
- Avoid oversized headings, oversized buttons, and giant (`2rem–3rem`) KPI card numbers.
- Avoid tiny unreadable text, especially for financial values.
- Arabic and English typography must both be visually balanced; never allow Arabic text/diacritics to appear cramped, clipped, or misaligned (`letter-spacing` forbidden in Arabic; `line-height >= 1.3`/`1.42`).
- **Do not use `Inter` for English content/body text where the established Miqat content font (`Miqat Text` via `--font-en-content`) is required.** Follow the exact established font assignments and tokens (`--font-en-display` = `'Cormorant Garamond'`, `--font-en-content` = `'Miqat Text'`, `--font-en-ui` / `body.accounts-workspace-page` = `'Inter'`).

### C. Content Containers & Card Consistency
- Do not leave text, statistics, actions, or related information floating without proper visual structure.
- Do not arbitrarily remove cards or containers just to make a layout appear simpler.
- Do not add decorative cards without a functional reason; keep related information grouped logically.
- Follow the established Miqat visual language; compare new components against existing approved pages before introducing any new pattern.

### D. Arabic / English Language Switching
- Language switching must be fully functional, never cosmetic.
- Every visible UI string must match the active language; no Arabic may remain in English mode (except approved brand/proper nouns) and no English UI labels may remain in Arabic mode.
- Translate buttons, labels, placeholders, table headers, status messages, empty states, dialogs, tooltips, validation messages, and JS-generated dynamic content.
- Never translate only static HTML while leaving JS-rendered content, event-handler strings, or active simulation steps untranslated.
- Language switching must update the active page immediately without a reload (via `onPageRefresh`) unless architecture requires otherwise, and preserve the selected language across navigation (`miqat_lang`).
- Never mix Arabic and English accidentally, and never leak raw i18n keys.

### E. RTL / LTR Direction
- Arabic mode must use `dir="rtl"`; English mode must use `dir="ltr"`.
- Always use logical CSS properties (`margin-inline`, `padding-inline`, `inset-inline`, `border-inline`, `text-align: start/end`) and avoid unnecessary hardcoded `left`/`right`.
- Isolate technical IDs, dates, sizes, and parentheticals (`dir="ltr"` / `<bdi>` / `.rep-table-mono`) so punctuation never reverses.
- Verify icons, arrows, navigation, drawers, tables, forms, dropdowns, and modal alignment in both directions.

### F. Light Mode
- Every card, table, modal, input, dropdown, tooltip, navigation element, and empty state must use Light Mode tokens (`--color-bg`, `--color-surface`, `--color-text`, `--color-border`).
- Do not leave dark surfaces, dark-mode borders, low-contrast text, or arbitrary raw `#fff` colors where surface tokens belong.
- Ensure switching Dark → Light updates all components completely across default, hover, focus, selected, disabled, and active states.

### G. Dark Mode
- Dark Mode ("Night in Makkah": `#172838` bg / `#22384B` surface) must be a complete theme, never a partial inversion.
- Never leave white cards/surfaces or dark text on dark backgrounds (especially `--color-primary` `#2B4E70` text on `#22384B` surfaces — use `--color-link` or `--color-text` classes instead).
- Never leave light-mode borders/shadows that break visually; update all inputs, tables, cards, modals, dropdowns, navigation, and status elements with Dark Mode tokens.
- Avoid harsh excessive contrast or pitch black (`#000000`); verify hover, focus, selected, disabled, and active states across Light ↔ Dark toggles.

### H. Status Colors
- Follow only the **4 canonical `.status-pill-*` classes** (`navy`, `amber`, `blue`, `slate`), and do **not** choose arbitrarily between `.status-pill-navy` and legacy `.status-pill-indigo` (always use `.status-pill-navy` for Confirmed / Verified / Completed in new work).
- Strictly enforce **Zero-Red / Zero-Green**; never introduce arbitrary red/green status colors, inline hex status overrides, or unapproved semantic tokens.

### I. Responsive Layout
- Guarantee **zero horizontal overflow** (`scrollWidth <= clientWidth`) at every supported viewport (`320px` through `1920px`) in both RTL and LTR.
- **Never** use `overflow-x: hidden` on root containers to conceal layout defects.
- Always apply `min-width: 0` on flex children and `minmax(0, 1fr)` on CSS grid tracks where shrinkage is needed.
- Contain wide tables inside `.acc-table-responsive`; ensure text, buttons, pills, cards, and forms never overlap or clip.
- Follow all 12 requirements of Section 12 (Section 6 of Responsive Guidelines).

### J. General Visual Quality
- Do not create an AI-looking generic dashboard; avoid oversized buttons, cards, icons, and headings.
- Do not invent random colors, fonts, gradients, shadows, or border radii.
- Avoid visual clutter, excessive decorative icons/badges, blur effects, or glassmorphism unless explicitly approved.
- Never sacrifice readability to cram content, never redesign approved shared components without authorization, and never invent a new pattern when an approved Miqat pattern already exists.
